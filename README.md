# vps-kit

Утилита для размещения нескольких Docker Compose-приложений на Ubuntu/Debian VPS. Добавляй проекты через **интерактивный мастер**: он задаёт вопросы, предлагает варианты и показывает настройки перед созданием. Для скриптов доступны команды с параметрами.

Сборка происходит в GitHub-hosted Actions. Готовые образы отправляются в GitHub Container Registry (GHCR), конфигурация — на VPS по SSH. На VPS выполняются скачивание образов и `docker compose up`; собственный Actions runner не нужен.

## С чего начать

Для нового сервера пройди шаги ниже. Если приложения уже работают на VPS, сначала прочитай [раздел о переносе](#уже-работающий-vps).

Понадобятся:

- VPS с Ubuntu 22.04/24.04 или Debian 12/13, systemd, доступом root/sudo и публичным IPv4;
- репозиторий приложения на GitHub с Compose-файлом и Dockerfile для сервисов с `build:`;
- права на Actions Secrets этого репозитория;
- доступ VPS к GHCR; для приватных образов — отдельный токен с правом чтения пакетов;
- открытые в firewall TCP 80, 443 и фактический SSH-порт сервера.

Сгенерированный workflow использует `ubuntu-latest` и без явной настройки платформы собирает для архитектуры runner. Для ARM VPS адаптируй сборку под целевую платформу до первого деплоя.

Короткий маршрут: **установка → мастер → production env → GitHub Secrets → доступ к образам → workflow в репозитории → первый деплой**. Добавление проекта само по себе приложение не запускает.

## 1. Установить утилиту на VPS

Выполняй **на VPS**. Скачай `install.sh`, просмотри его и затем запусти:

```bash
curl -fsSLO https://raw.githubusercontent.com/MorkovnySok/vps-kit/main/install.sh
less install.sh
sudo bash install.sh --ip PUBLIC_IPV4
```

Замени `PUBLIC_IPV4` на публичный IPv4 сервера. Если sshd уже слушает нестандартный порт, укажи его:

```bash
sudo bash install.sh --ip PUBLIC_IPV4 --ssh-port 2222
```

`--ssh-port` сохраняет порт для будущего деплоя, **не меняет настройки sshd**. Без `--ip` используется сохранённый IP, иначе автоопределение. Без `--ssh-port` используется сохранённый порт, иначе 22. Справка установщика доступна без sudo: `bash install.sh --help`.

Установщик добавляет Docker Engine/Compose, Caddy, GitHub CLI (`gh`), Python и необходимые системные пакеты; создаёт пользователя `deploy`, каталоги проектов и команду `vpsctl`. Существующие Docker/Compose и Caddy сохраняются, если они уже установлены. **Caddyfile дополняется строкой импорта** `/etc/caddy/vps-kit/*.caddy`; перед изменением существующего файла создаётся копия.

Firewall, парольный вход и SSH-порт остаются под твоим управлением. Установщик не переносит старые приложения/runners и не удаляет контейнеры или volumes. Открой 80/443 и свой SSH-порт в панели провайдера/host firewall. Не открывай Docker API.

## 2. Добавить проект через мастер

Выполняй **на VPS**:

```bash
sudo vpsctl
```

В главном меню выбери **«Добавить проект»**. Также можно открыть мастер напрямую:

```bash
sudo vpsctl project add
```

Управление: **↑/↓ и Enter** либо номер и Enter. В простом или небольшом терминале показывается нумерованный список. Enter в вопросе принимает ответ в скобках. Ctrl+C отменяет ввод; Esc отменяет выбор в меню со стрелками.

Мастер спросит:

| Вопрос | Что указать |
| --- | --- |
| Репозиторий | `OWNER/REPO` или ссылку `https://github.com/OWNER/REPO` |
| Имя проекта | Уникальное имя на VPS, например `myapp`; оно задаёт имя Compose-проекта и каталога |
| Compose-файл | `compose.yaml`, `docker-compose.yml` или путь от корня репозитория, например `deploy/compose.yaml` |
| Ветка | Ветку для автоматического деплоя, обычно `main` |
| Порт | Порт приложения **на VPS**, например `8081`, а не порт внутри контейнера |
| Адрес | Бесплатный адрес sslip.io или свой домен |
| Caddy | Создать сайт с reverse proxy или оставить маршрутизацию для ручной настройки |

Имя и порт проверяются на конфликты с зарегистрированными проектами. Предложенный порт ещё может быть занят сторонним приложением — проверь это на уже работающем VPS. Если публичного IP в настройках нет, мастер предлагает свой домен; для GitHub Secrets всё равно потребуется настроенный IPv4.

Перед созданием мастер показывает все ответы. Можно выбрать **«Создать проект»**, **«Изменить ответы»** или **«Отмена»**. До подтверждения файлы и ключи не создаются. При обычной ошибке регистрации созданные в этой попытке файлы и ключ откатываются; существующие данные приложения сохраняются.

После успеха появятся:

- `/opt/apps/myapp/shared/.env` с правами `600` для production-переменных;
- отдельный ключ для ограниченного SSH-деплоя этого проекта;
- метаданные проекта в `/etc/vps-kit/projects/myapp.json`;
- сайт Caddy, если выбран автоматический маршрут.

Для sslip.io адрес имеет вид `myapp.203-0-113-10.sslip.io` (здесь IP приведён как пример). Для своего домена настрой DNS A-запись на IP VPS. До запуска приложения сайт Caddy может отвечать 502; HTTPS также требует доступного DNS и выпуска сертификата.

Уже знакомые параметры можно использовать как начальные ответы мастера:

```bash
sudo vpsctl project add myapp --repo OWNER/REPO --port 8081 --interactive
```

Для автоматизации полный набор обязательных параметров запускает создание без вопросов:

```bash
sudo vpsctl project add myapp --repo OWNER/REPO --port 8081 \
  --compose compose.yaml --branch main

# Свой домен
sudo vpsctl project add another --repo OWNER/ANOTHER --port 8082 \
  --domain app.example.com
```

Опция `--no-caddy` оставляет настройку reverse proxy тебе. Если домен уже объявлен в основном Caddyfile, используй эту опцию, чтобы продолжить с существующим сайтом.

## 3. Подготовить Compose и production-переменные

**В репозитории приложения** публикуй веб-порт только на loopback VPS. Левый порт должен совпадать с выбранным в мастере:

```yaml
services:
  web:
    build: ./web
    ports:
      - "127.0.0.1:8081:80"
    restart: unless-stopped
```

При деплое отклоняются публичные привязки (`"8081:80"`, `"0.0.0.0:8081:80"`) и `network_mode: host`. Не публикуй PostgreSQL наружу: сервисы внутри Compose могут обращаться к нему по имени. Для БД и других постоянных данных используй **именованные volumes**. Относительный bind mount `./db:/...` попадёт внутрь отдельного релиза и не обеспечивает сохранение данных между релизами.

**На VPS** заполни файл, созданный мастером:

```bash
sudo nano /opt/apps/myapp/shared/.env
```

Этот файл используется при запуске Compose и не передаётся из GitHub. Если сервису нужен `env_file`, укажи `.env` рядом с основным Compose-файлом. Разные файлы вроде `.env.production` автоматически не создаются.

Если Compose требует переменные вида `${DB_PASSWORD:?}`, добавь **в корень репозитория приложения** `.env.ci` с безопасными заглушками для сборки. Workflow загружает его как shell-файл; простой формат `KEY=value` подходит. Не помещай туда production-пароли или токены. Смотри [пример Compose](examples/compose.yaml) и [пример .env.ci](examples/.env.ci).

## 4. Настроить GitHub Secrets

Выполняй **на VPS**:

```bash
sudo gh auth login --web
sudo vpsctl github configure myapp
```

Команда загружает четыре Actions repository Secrets **в репозиторий приложения**, выбранный в мастере:

| Secret | Назначение |
| --- | --- |
| `DEPLOY_HOST` | Публичный IPv4 VPS |
| `DEPLOY_PORT` | Сохранённый SSH-порт |
| `DEPLOY_SSH_KEY` | Отдельный приватный ключ проекта |
| `DEPLOY_KNOWN_HOSTS` | Публичный SSH host key этого VPS, с учётом нестандартного порта |

Потребуются права на изменение Secrets репозитория. Команда изменяет эти Secrets, но не публикует исходники и не добавляет workflow. В главном меню доступно то же действие с выбором проекта.

После успешной загрузки временный приватный ключ удаляется с VPS. Если операция прервалась, ключ остаётся для повтора в каталоге root `/root/.local/share/vps-kit/pending-keys/`. Устрани причину и повтори `github configure`. После успеха повторная загрузка удалённого ключа не предусмотрена; команда также не реализует ротацию ключей.

По завершении можно убрать авторизацию GitHub CLI с сервера:

```bash
sudo gh auth logout
```

### Разрешить VPS скачивать приватные GHCR-образы

Это отдельная авторизация. Выполни **на VPS**:

```bash
sudo vpsctl registry login YOUR_GITHUB_LOGIN
```

На запрос Docker `Password` введи отдельный GitHub PAT (classic) с `read:packages` и доступом к пакетам приложения. Для организации проверь SSO и правила доступа к Packages. Обычно вход нужен один раз для пользователя `deploy`; публичные образы могут скачиваться анонимно.

Токен сохраняется в конфигурации Docker системного пользователя `deploy` без встроенного менеджера секретов. Не передавай его в аргументы команды, не коммить и периодически меняй.

## 5. Добавить workflow в репозиторий приложения

**На VPS** создай файл:

```bash
vpsctl workflow myapp --output "$HOME/deploy-myapp.yml"
```

`--output` откажется перезаписывать существующий файл. Старый вариант `vpsctl workflow myapp > deploy.yml` тоже работает, но `>` может перезаписать файл по правилам shell.

**На своём компьютере**, в локальном checkout приложения, скопируй результат с VPS:

```bash
mkdir -p .github/workflows
scp USER@PUBLIC_IPV4:~/deploy-myapp.yml .github/workflows/deploy.yml
git add .github/workflows/deploy.yml
git commit -m "Add VPS deployment workflow"
git push
```

Замени `USER` на пользователя SSH, в домашнем каталоге которого сохранён workflow. Для нестандартного SSH-порта добавь `scp -P 2222 ...`. Это пример для shell с `mkdir -p`; на Windows каталог можно создать через редактор или `New-Item -ItemType Directory -Force .github/workflows`.

После push в выбранную ветку открой вкладку **Actions** репозитория приложения. Workflow также можно запустить вручную через `workflow_dispatch`. Kit не ограничивает ветку ручного запуска; для production настрой branch protection и при необходимости GitHub Environment approvals в workflow.

Что происходит при запуске:

1. GitHub-hosted runner получает исходники и входит в GHCR через `GITHUB_TOKEN` с `packages: write`.
2. Сервисам с `build:` задаются образы `ghcr.io/owner/repo-service:sha-<commit>`; они собираются и публикуются. Готовые `image:` вроде PostgreSQL не пересобираются.
3. Checkout и `.vpskit.images.yaml` упаковываются и отправляются на VPS по SSH с ограниченным ключом.
4. Приёмник проверяет архив, подключает серверный `.env`, проверяет Compose/порты и скачивает образы.
5. Выполняется `docker compose up -d --no-build --wait` со стабильным именем проекта.
6. При неудаче приёмник пытается запустить предыдущий релиз. После успеха обновляет указатель `current`.

Отправитель исключает `.env`/`.env.*` из архива. Приёмник **отклоняет весь архив**, если внутри всё же есть такие файлы, `.git`, `.ssh`, symlink, hardlink, устройство или путь с `..`. Он не пропускает неподдерживаемые записи молча. Поэтому репозиторий с symlink-файлами потребует адаптации упаковки. Ограничения архива: 25 000 записей и 2 GiB распакованных данных.

## Команды и справка

| Команда | Что делает | Права |
| --- | --- | --- |
| `sudo vpsctl` | Открывает главное меню | Зависит от выбранного действия |
| `sudo vpsctl project add` | Запускает мастер добавления | root |
| `sudo vpsctl project add NAME --repo OWNER/REPO --port PORT` | Добавляет без вопросов | root |
| `sudo vpsctl github configure [NAME]` | Загружает deployment Secrets | root, авторизация `gh` |
| `sudo vpsctl registry login [LOGIN]` | Входит в GHCR для `deploy` | root |
| `vpsctl workflow [NAME] --output FILE` | Сохраняет workflow | Чтение метаданных, запись в выбранный файл |
| `vpsctl status` | Показывает проекты и `docker ps` | Для контейнеров нужен доступ к Docker |
| `sudo vpsctl doctor` | Проверяет Docker, Compose, Caddy и GHCR | Рекомендуется root |
| `vpsctl help [COMMAND ...]` | Показывает подробную справку | Без root |

Без имени `workflow` и `github configure` предлагают выбрать проект в терминале; `registry login` спрашивает логин. Квадратные скобки в таблице означают необязательный аргумент, их вводить не нужно.

```bash
vpsctl --help
vpsctl project add --help
vpsctl help github configure
vpsctl workflow --help
bash install.sh --help
```

Если не передать команду, `vpsctl` открывает меню в интерактивном терминале, а при перенаправленном вводе/выводе печатает справку. Для автоматизации передавай все обязательные параметры: она не зависнет в ожидании ответов мастера. Коды выхода: `0` — успех или явная отмена мастера, `1` — ошибка выполнения/проверки, `2` — ошибка аргументов, `130` — прерванный ввод.

## Проверка и частые проблемы

Выполняй **на VPS**:

```bash
sudo vpsctl doctor
sudo vpsctl status
sudo docker compose ls
```

`doctor` проверяет только базовую инфраструктуру. HTTP 401 от GHCR ожидаем: реестр доступен, но запрос анонимный. Эта проверка не подтверждает права на конкретный пакет, работу DNS/TLS или готовность HTTP API. При проблеме команда возвращает код выхода 1.

| Симптом | Что проверить |
| --- | --- |
| `vpsctl: command not found` | Установщик должен завершиться на VPS; команда ставится в `/usr/local/bin/vpsctl` |
| Мастер не открывается | Нужны интерактивные stdin/stdout; подключись по SSH без pipe/redirect или передай параметры |
| `gh` не авторизован | Выполни `sudo gh auth login --web`; авторизация обычного пользователя отличается от root |
| GHCR недоступен / HTTP 000 | Сеть, DNS, доступ VPS к `ghcr.io`; альтернативной доставки образов через SSH пока нет |
| Ошибка `unauthorized` при скачивании | `sudo vpsctl registry login LOGIN`, `read:packages`, доступ к пакету и SSO организации |
| `Host key verification failed` | Совпадают ли IP, SSH-порт и ключ сервера с `DEPLOY_*`; после смены host key Secrets нужно обновить отдельно |
| Caddy отклонил добавление | Исправь `/etc/caddy/Caddyfile`, проверь конфликт домена и повтори мастер; можно выбрать ручной маршрут |
| Сайт отвечает 502 | Успешен ли деплой, запущен ли веб-контейнер, совпадает ли порт Compose с портом проекта |
| HTTPS не работает | DNS A/sslip.io, TCP 80/443, логи `sudo journalctl -u caddy -n 100 --no-pager` |
| Не задана переменная Compose | Production `.env` на VPS; безопасная `.env.ci` в корне репозитория для CI |
| Неподдерживаемая запись в архиве | Symlink/hardlink или исключаемые файлы в checkout: адаптируй упаковку workflow |
| Приложение запущено, но не готово | Добавь healthcheck: без него `--wait` проверяет `running`, а не готовность HTTP API |

Чтобы посмотреть приложение вручную после успешного деплоя (замени `myapp`):

```bash
cd /opt/apps/myapp/current
sudo docker compose -p myapp -f compose.yaml -f .vpskit.images.yaml ps
sudo docker compose -p myapp -f compose.yaml -f .vpskit.images.yaml logs --tail 100
```

Если Compose лежит в `deploy/compose.yaml`, укажи этот путь вместо `compose.yaml`. При первом неудачном деплое `current` ещё нет: посмотри вывод GitHub Actions и список `sudo docker ps -a`.

## Уже работающий VPS

Автоматической миграции старых runners, Compose-проектов и volumes нет. Перед переносом:

1. Сделай резервную копию БД и постоянных данных.
2. Проверь существующие Compose-имена, порты и Caddy-маршруты; мастер видит только проекты, зарегистрированные в kit.
3. При сохранении данных укажи реальные имена существующих volumes через `name:`/`external:`. Совпадения нового slug недостаточно, если раньше Compose использовал другое имя проекта.
4. Подготовь новый workflow, production `.env`, Secrets и доступ к образам.
5. Отключи старый механизм деплоя перед запуском нового. Не запускай два workflow для одного приложения одновременно.

Если домен уже обслуживается существующим Caddy-сайтом, в мастере выбери ручную маршрутизацию. При этом проверь, что прежний reverse proxy направлен на новый loopback-порт.

## Файлы, ограничения и безопасность

| Путь на VPS | Содержимое |
| --- | --- |
| `/etc/vps-kit/config.json` | Публичный IPv4 и SSH-порт |
| `/etc/vps-kit/projects/<slug>.json` | Метаданные приложения |
| `/etc/caddy/vps-kit/<slug>.caddy` | Сайт Caddy, если выбран автоматический маршрут |
| `/opt/apps/<slug>/shared/.env` | Production-переменные; владелец `deploy`, режим `600` |
| `/opt/apps/<slug>/releases/` | Сохранённые релизы |
| `/opt/apps/<slug>/current` | Ссылка на последний успешный релиз |
| `/root/.local/share/vps-kit/pending-keys/` | Ключи до успешной загрузки Secrets |
| `/home/deploy/.ssh/authorized_keys` | Ограниченные ключи приёмника |

Пользователь `deploy` имеет Docker-доступ, то есть **практически root-доступ**. Ограничение SSH-команды не изолирует недоверенные репозитории друг от друга и не делает произвольный Compose безопасным. Используй доверенные репозитории и защищай deployment Secrets.

Релизы и Docker-образы не удаляются автоматически. Следи за свободным местом. Резервных копий, команды удаления проекта, ротации ключей и ручного rollback через `vpsctl` пока нет. Автоматический rollback — попытка восстановления контейнеров; он не откатывает миграции БД, данные volumes или изменения общего production `.env`. Первый неудачный деплой не имеет предыдущего релиза для восстановления.

Для нескольких Compose-файлов, profiles, приватных build secrets, нестандартных build contexts и целевых архитектур workflow нужно адаптировать. Теги по SHA используются для собранных сервисов; готовые `image:` могут оставаться изменяемыми, если не закрепить digest. Не передавай production-пароли через Docker build args.

Утилита проверяется офлайн и в локальном псевдотерминале. Полная установка на чистом VPS, GitHub Actions/GHCR, выпуск TLS и восстановление реального приложения ещё не проверены сквозным тестом.

## Разработка

`install.sh` собирается из прозрачных исходников `src/`; после изменения исходников пересобери его. Дополнительные UI-библиотеки на VPS не нужны: мастер использует стандартную библиотеку Python.

На Linux или в WSL:

```bash
# Только для среды разработки/тестов: требуется PyYAML
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r requirements-dev.txt
bash build.sh
python3 tests/test_offline.py
python3 tests/test_cli.py -v
```
